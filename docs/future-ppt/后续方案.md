# AI 原生动态演示工具：基于 HyperFrames 的二次开发路线

> 版本：v0.2（开发方向草案）  
> 更新时间：2026-10-15  
> 项目阶段：技术基线验证 → 核心交互 PoC → MVP  
> 上游项目：[heygen-com/hyperframes](https://github.com/heygen-com/hyperframes)  
> 文档性质：**指导下一步研发，不是对现有源码已经完成的审计。** 具体 API、模块行为和许可证范围以所固定的上游 Commit 与本地验证为准。

---

## 0. 先说结论

我们暂时**不从零开发动画引擎，也不立即全面重构 HyperFrames**。

以 HyperFrames 作为首选底座，先 Fork 并跑通官方流程，再围绕用户真正关心的体验做小范围验证：

> AI 完成约 99% 的演示创作；用户直接像修改 PPT 一样改文字、移动 5px、调整动画起点和终点，然后继续演示或分享。

只有当上游能力确实阻碍这一目标时，再修改底层 Core、SDK 或时间模型。我们的差异化不在于「支持 AI 写动画代码」，而在于**生成之后的作品，仍能被普通用户以确定性的方式快速修改、交互和持续使用**。

### 技术方向的四条红线

1. **AI 与人编辑的是同一份作品**。不能让 AI 修改源码后，手工编辑的内容失效；也不能有两个互相竞争的“真实数据源”。
2. **局部修改不应导致非目标元素重做**。改标题、移动位置和时间微调，优先产生可追踪的局部操作。
3. **时间轴是底层能力，不是用户操作门槛**。普通用户优先看到画布、属性与简单动画控制，高级时间轴按需展开。
4. **播放是演示，不只是导出视频**。页面区间、跨页对象与点击交互属于核心设计；视频导出只是可选输出。

## 1. 产品定位与边界

### 1.1 一句话定位

**像编辑 PPT 一样，精确修改由 AI 生成的专业动态 Web 演示。**

### 1.2 典型工作流

1. 用户提供主题、素材或大纲，让 AI 生成完整的动态演示初稿。
2. 系统生成页面结构、对象、动画和必要的交互，并支持直接预览。
3. 用户发现标题偏右：选中标题 → 左移 5px（拖动、方向键或数值输入）。
4. 用户觉得某个 Logo 运动太快：选择其运动区间 → 微调起止位置或动画时间。
5. 用户修改一段文字：原来的动效与布局尽量保持，不重新生成整个页面。
6. 用户全屏播放，点击触发下一阶段、展开细节，或发布 Web 演示链接。

### 1.3 不做什么

- 初版不与 AE 比拼复杂特效总量、合成节点系统或专业后期制作。
- 初版不追求任意 HTML/JS 都能无损转换成可编辑对象。
- 初版不把「用户手工从零制作复杂动画」作为主流程。
- 初版不承诺完整、无损的 PowerPoint PPTX 动画导出。
- 初版不建立云端协作、素材商城、支付系统或大规模视频渲染集群。
- 初版不要求每个物体独占一个 `canvas`：对象实例独立、时间轴独立，但底层渲染上下文可以共享。

### 1.4 目标用户（第一批）

- 需要在发布会、产品介绍、技术分享中展示高质量动效的产品经理、设计师、开发者。
- 希望 AI 负责复杂动效，又希望自己能精确调整细节的人。

**暂不主攻**只需要静态工作汇报 PPT 的用户，以及依赖 AE 全功能的专业动效团队。

## 3. 架构策略：先做适配层，再决定是否换数据模型

### 3.1 不要立刻推翻 HTML Composition

HyperFrames 以可编辑 HTML Composition 为中心，Studio/SDK/Player/渲染都围绕这套契约运转。

我们想要的长期形态是：

```text
用户自然语言 / 素材
        │
        ▼
    AI 生成与修改
        │ 结构校验与增量操作
        ▼
作品编辑协议（稳定元素 ID、属性、动作、关联）
        │
        ├── 人工直接编辑（文字/位置/路径/时长）
        ├── AI 局部编辑
        └── Undo / Redo / 保存与版本
        │
        ▼
HyperFrames SDK / Composition 适配层
        │
        ├── Studio Preview / Player
        ├── 演示状态与交互
        └── 视频输出（后续）
```

这里的“作品编辑协议”最初**只做轻量命令/补丁层**。不要在还未验证 SDK 时，就另建一套 JSON 场景真源并要求与 HTML 双向同步。

### 3.2 第一项架构决策：谁是 Single Source of Truth？

先做对比实验，再从以下两个选项中选择一个。

**方案 A（优先验证）：上游 HTML Composition + SDK Overrides 为真实来源。**

- AI 生成/修改受约束的 Composition。
- 用户编辑通过 SDK 结构化操作或可控 Patch 落地。
- 元素使用稳定 ID，历史记录、预览和导出依据同一数据。
- 优点：改动小，兼容上游；风险：独立对象轨道和跨页机制未必能自然表达。

**方案 B（需要证据后再采用）：自定义 Scene / Instance / Motion / Binding 为真实来源。**

- AI 产生受校验的场景声明，由编译层输出 HyperFrames HTML/动画。
- 编辑器修改场景声明，统一编译预览。
- 优点：适合长期独立轨道；风险：需要解决与 Studio 原始 HTML 编辑、SDK Patch 和外部源码改动的同步冲突。

**决策规则：**只有当方案 A 无法稳定实现“跨页对象 + 局部可编辑动画 + AI 与手工修改无损共存”，才升级为方案 B。无论选择哪一个，都必须明确唯一真实来源，另一种格式只能是派生视图或可控导入。

## 4. 我们最终希望具备的时间模型

这些是**产品层面的目标抽象**，不是声称上游已经完全支持。

### 4.1 统一总时间轴

整个演示有一条连续的全局时间轴，支持播放、暂停、拖动、跳帧、点击触发与精确定位。

### 4.2 页面是时间区间，不是元素容器

例如：

```text
Global timeline: 0 ───────────────────────────── 720f
Page A:         [0──────────────300)
Page B:                         [300────────────720)
Logo binding:             [200────────────────680)
Logo local:                0f → ... → 480f
```

Logo 可以跨越页面边界继续运动。改变 Page A 长度时，必须有清楚的绑定策略，不能让其运动莫名中断或丢失。

### 4.3 元素有自己的局部运动定义

实例拥有独立属性轨道（位置、缩放、旋转、透明度等）。全局 Binding/Clip 决定该实例的局部时间如何映射到全局时间。

基础关系：

```text
localTime = (globalTime - bindingStart) × speed + localOffset
```

循环、倒放、事件触发需另定义确定性规则。实例的**可见范围**与它的**关键帧运动区间**应分离。

### 4.4 动画应支持任意时间准确求值

任何时刻的结果主要由作品定义、时间与可复现的交互状态决定，不依赖“必须先播放到该帧”。

对交互演示，需要额外定义触发事件记录与状态恢复；否则 seek、回退、录屏或分享会不一致。

### 4.5 跨页时需定义合成语义

重点确认：

- 页面到底切换的是背景、视口状态还是图层组？
- 哪些对象跟随页面、哪些对象跨页常驻？
- 页面切换时图层顺序、遮罩、镜头和点击区域如何处理？
- 用户在某页编辑跨页元素时，修改的是实例本身还是某个时间位置的关键帧？

第一版采用清楚、易解释的默认规则，避免引入无法预测的自动行为。

## 5. 我们真正要做的产品交互

### 5.1 默认是 PPT 式直接编辑，不是 AE 式复杂轨道

- 点击文字直接修改。
- 点击对象显示控制框、坐标、宽高、旋转、透明度。
- 拖动直接改位置；方向键微调；数值框支持精确输入（如 X - 5px）。
- 拖动后仍能 Undo/Redo，保存刷新后结果一致。
- 选择运动元素时，默认只显示「起点」「终点」「持续时间」等少量控制。
- 高级用户可进入属性轨道与关键帧编辑。

### 5.2 微调不能随意破坏动画

**最关键的交互歧义：**用户在某一帧拖动对象时，究竟想修改什么？

初版必须显式提供三种模式（可简化 UI 文案）：

1. **移动整个动画**：所有关键帧整体平移 5px，保留原轨迹形状。
2. **修改当前帧 / 关键帧**：改变对应节点，必要时新建关键帧。
3. **修改最终位置**：只调整动画结束状态，起点不变，中间轨迹重新计算。

默认操作应让用户容易理解；不能无提示地生成大量关键帧或意外改变整段动画。

### 5.3 AI 与人工编辑的边界

- AI：生成完整演示、增加场景、调整设计语言、重编复杂动效。
- 人：文字校正、对齐、位置微调、尺寸和节奏等确定性修改。
- AI 再次修改时：只改指定范围，优先保留其他人工修改；冲突应可见、可撤销。

第一阶段不需要真正“零代码”覆盖所有动画，只需要高频微调体验足够可靠。

### 5.4 演示态可以编辑，但须区分权限

用户希望在演示过程中改字、改对象位置：可以支持**演示者在授权编辑模式中直接修改**，并同步预览；观众看到的只应是演示态。发布链接不应默认让任何访问者修改源作品。

初版先完成本地或登录用户的演示内快捷编辑，再考虑多人实时协作。

## 6. 分阶段开发路线

> 建议按 **Gate（通过/不通过）** 推进，不把时间估算当作事实承诺。下方“建议工作量”只用于排优先级，取决于开发人数与现有代码质量。

### Phase 0 — 固定上游基线 + 源码审计（P0）

**目标：先证明能运行、能修改，再谈重构。**

任务：

- [ ] Fork 官方仓库，配置 `origin`（自己的仓库）和 `upstream`（官方仓库）。
- [ ] 固定一个已验证 Commit/Tag，在项目日志记录 SHA、依赖版本、运行环境。
- [ ] 按仓库当前 README / `AGENTS.md` / `package.json` 安装依赖、构建、启动 Studio，保留运行记录。
- [ ] 运行至少一个普通动画案例和一个 Slideshow 案例，确认预览与演示可用。
- [ ] 检查 Studio、SDK、Player、Core 的入口与编辑数据流，画出“编辑操作 → 保存 → 预览”的简图。
- [ ] 确认 Apache-2.0 LICENSE、NOTICE（如有）、第三方资源及依赖许可证范围。
- [ ] 写 `UPSTREAM_BASELINE.md`，列出「已复用/需扩展/暂不处理」。

**验收 Gate 0：**在本地能够稳定运行并演示一个官方项目；能指出一个文本编辑从 UI 到文件/覆盖层的完整写入路径；固定 SHA 可复现。

### Phase 1 — 精确微调 PoC（P0）

**目标：证明“AI 生成后，用户左移 5px”不是一句口号。**

任务：

- [ ] 制作含标题、图片、SVG 和多个动效的测试作品。
- [ ] 测试 SDK 的 `data-hf-id`、文本编辑、属性修改、Patch/Overrides、Undo/Redo。
- [ ] Studio 中实现或优化选中元素后的 X/Y 数值框、键盘微调和可拖动控制框。
- [ ] 验证移动整个轨迹 / 修改终点位置的差异与正确性。
- [ ] 保存、刷新、重新打开、反复 seek，确认修改一直存在且没有动画漂移。
- [ ] 做同一页面的 AI 局部更新，验证人工改动是否保留；记录失败模式。

**验收 Gate 1（建议目标）：**

- 普通用户能在无需打开代码编辑器的情况下，完成「改标题、左移 5px、调整动画终点」三项任务。
- 每次局部修改都能撤销；保存刷新后保持一致。
- 重放和跳到相同时间点，得到一致画面。
- 对失败情况可明确定位是 SDK/Studio 限制、数据契约限制还是操作规则问题。

### Phase 2 — 连续时间轴与跨页实例 PoC（P0）

**目标：验证我们与普通 Slideshow 的真正差异。**

任务：

- [ ] 制作两个页面时间区间，共用一个跨页 Logo 实例。
- [ ] 让 Logo 在第一页中途开始运动，跨页边界后继续，不重建或闪断。
- [ ] 支持 Logo 的局部时间定义与全局 Binding 映射。
- [ ] 拖动全局播放头可预览任意帧，包括页面切换前后。
- [ ] 缩短/拉长页面区间，验证对跨页对象影响符合明确规则。
- [ ] 对页面背景、局部对象、跨页对象的层级顺序制定默认规则。

**验收 Gate 2：**一个实例跨越两个页面区间连续运动；seek 前后结果一致；修改对象轨道不要求分别编辑两页的重复对象。

**架构分叉点：**如无法在上游 Composition/SDK 模型中稳定表达，再单独立项扩展 Instance + Binding；不要把“想象中的最终架构”直接铺到所有包里。

### Phase 3 — AI 创作与局部修改闭环（P0/P1）

**目标：AI 生成可编辑作品，用户微调后 AI 再修改也不会随意覆盖。**

任务：

- [ ] 定义一个最小 AI 输出契约：稳定 ID、允许的元素种类、时间规则、可编辑属性。
- [ ] 提供创建 / 修改 / 校验 / 预览 / 修复的工具调用流程。
- [ ] 实现指定对象或指定区间的局部修改，避免无差别重写整个 Composition。
- [ ] 所有 AI 变更保留操作记录，支持撤销及人工改动的冲突检测。
- [ ] 失败时回滚到最近稳定版本，不把半生成状态覆盖到正式作品。
- [ ] 做 3 个标准测试任务：产品介绍、技术架构讲解、数据演示。

**验收 Gate 3：**AI 生成一份可演示作品；用户修改标题与位置；随后请求 AI 修改另一个对象，原人工修改仍保留，且结果可检查与回退。

### Phase 4 — 演示交互与 MVP 交付（P1）

**目标：真正能在现场讲解，而不只是播放视频。**

任务：

- [ ] 全屏演示、暂停/继续、按键推进、跳到指定演示阶段。
- [ ] 点击热点触发局部动画 / 展开内容 / 返回原状态。
- [ ] 演示者快捷编辑入口（与公开观众视图隔离）。
- [ ] 作品本地保存与重新加载；可分享 Web 演示作为下一步交付目标。
- [ ] 发布前的错误检查：字体、图片丢失、关键帧冲突、运行时异常。
- [ ] 保留上游可用的演讲备注/分支能力，不重复开发已成熟的功能。

**验收 Gate 4：**完整演示可连续播放并被演讲者控制；点击交互不会破坏其他对象的动画状态；演示者能快速修改文本并保存。

### Phase 5 — 再决定后续扩展（暂不进入 MVP）

多人实时协作、数据实时绑定、复杂动效预设库、录制与视频渲染规模化、PPTX 有损导出、完整在线 SaaS、移动端深度编辑等，依据试用数据排序。

## 9. 质量与验证：比“能跑起来”更重要

### 9.1 最小回归用例

1. **编辑稳定性**：标题 `x = 200` 改到 `195`；保存、重开仍为 `195`。
2. **精确动画**：修改某个结束关键帧后，其他关键帧和无关元素不变化。
3. **Seek 一致性**：在同一时间点，多次 seek 后画面一致；不会因播放历史不同而漂移。
4. **跨页连续性**：边界前后 Logo 运动连续，图层不意外消失或跳位。
5. **AI 协作**：AI 修改配色后，用户手工改过的标题文字/坐标不被覆盖。
6. **可撤销性**：AI 与人工修改都能记录变更来源并在允许范围内回退。
7. **交互回放**：点击展开后返回，局部与全局状态恢复正确。
8. **发布隔离**：匿名观众不能通过演示链接修改或获取作者编辑权限。

### 9.2 体验目标（待用户测试，不是现有性能事实）

- 常见“改标题、移动 5px”操作无需打开源码或重新请求 AI。
- 用户一眼能看出当前是在移动整个轨迹、修改一个关键帧，还是修改动画终点。
- 同样的 3 项微调任务，让不懂 AE 的用户完成，再与现有 HyperFrames Studio 的操作步数和耗时比较。
- 记录 AI 生成后用户需要修正的数量、修正耗时、回滚次数、生成后可编辑率，而不是只看生成动画是否好看。

### 9.3 必须记录的技术风险

| 风险           | 具体表现                          | 缓解方式                                       |
| -------------- | --------------------------------- | ---------------------------------------------- |
| 双数据真源     | HTML 被修改、JSON 轨道未同步      | 一开始只保留一套权威来源；另一套必须可重新生成 |
| AI 破坏引用    | 整段 HTML 重写导致稳定 ID 失效    | 稳定 ID、受限改动、Patch 与结构校验            |
| 属性冲突       | CSS/GSAP/编辑器同时写 `transform` | 明确动画属性所有权与合成策略                   |
| Seek 非确定性  | 跳帧、重放结果不一致              | 禁止不可控时钟/随机副作用，建立逐帧回归        |
| 页面模型冲突   | 跨页对象被页面生命周期销毁        | 页面区间与实例存活、绑定分离                   |
| 上游迭代快     | Fork 难以持续合并                 | 固定版本、薄扩展、定期选择性同步               |
| 脚本安全       | AI 生成 HTML/JS 进入演示环境      | iframe 隔离、CSP、资源限制、受信任能力边界     |
| 开源与素材授权 | 代码与第三方素材权限混淆          | 检查 LICENSE/NOTICE/依赖/SVG/字体/音视频等     |

## 10. 开源使用与工程协作规则

- HyperFrames 主仓库当前标注 Apache-2.0，允许依协议复制、修改、再分发和商用；应保留适用许可证与版权声明，标明修改，遵守 NOTICE 要求（如适用）。
- **代码许可证不自动覆盖**商标、品牌素材、示例中的第三方音视频/字体及其他资产。发布产品前单独审查。
- 修改上游文件，优先写清用途及为什么不能通过扩展层实现。
- 保留上游 `upstream` remote，记录每次同步的 Commit 范围和冲突处理结果。
- 在我们的 `AGENTS.md` 中约束 Codex：先读 HyperFrames 现有类型和接口、优先扩展不重写、修改后运行相关测试、不得未经确认迁移全仓结构。
- 安全处理 AI 生成的 HTML/JS：编辑器和演示页面应隔离执行，不应默认为任意生成代码授予文件系统、用户凭据或私有接口权限。

## 12. 什么时候应该停止 Fork，改为独立开发？

不要因为上游很热门就长期绑定，也不要因为某个 API 不符合习惯就过早脱离。

出现以下情况应重新评估底座：

- 核心时间模型根本无法在上游稳定表达，且每次改动都要侵入多处底层逻辑。
- 文字/位置微调仍高度依赖源代码修补，用户体验难以稳定。
- SDK/Studio 的编辑协议与 AI 输出协议反复冲突，无法确定唯一真源。
- 上游升级成本持续超过复用所节省的成本。
- 安全隔离、商用交付或性能指标与上游设计发生不可接受的结构性冲突。

如果只是 UI 不符合 PPT 用户习惯，则通常**先改产品外壳和编辑交互**，不是重写时间轴引擎。
