# AI 原生动态演示工具｜产品需求文档

> 版本：v0.1（产品概念与 MVP 需求）  
> 更新日期：2026-10-15  
> 文档状态：方向已明确，部分细节待验证  
> 暂定名称：AI 原生动态演示工具（HTML-PPT）

## 1. 一句话定义

**像编辑 PPT 一样，修改由 AI 生成的专业动态演示。**

用户用自然语言描述想展示的内容，AI 负责内容组织、视觉设计、动画编排和基础交互；用户主要通过画布直接操作完成最后少量、精确的修改，例如改标题、左移 5px、调整运动起点和终点、修改动画节奏。作品以可持续编辑、可交互的 Web 动态演示形式运行和分享。

这里的“AI 完成 99%，人调整 1%”是**产品体验目标**，不是现阶段模型质量承诺，也不是对每个任务的量化预测。

## 2. 为什么做

现有路线存在不同侧重点：

- **传统 PPT**：编辑文本、图形、排版和现场讲解非常方便，但复杂连续动效制作成本较高。
- **AE 等专业动画软件**：擅长专业动画与复杂合成，但面向演示场景的内容微调、运行时交互和 Web 分发并不是核心工作流。导出为视频后，常规内容修改往往要回到原工程重新输出；模板化方案能解决部分情况，但修改范围由模板约束。
- **Codex / AI 直接操作 AE 或编写动画代码**：可以大幅降低创作难度，但用户若想立即完成“向左 5px”“修改几个字”这样的确定性修改，往往仍需要进入复杂工程或重新发起一次 AI 操作。
- **现有 AI-PPT**：较擅长快速生成页面与排版，但通常不是以复杂对象级连续动效、跨页动画和交互式 Web 演示为中心设计。

本产品的机会不在于“AI 能写动画”，而在于**AI 高质量生成后，结果仍能像普通 PPT 一样被直接、准确、低成本地修改和交付**。

### 2.1 与 Codex + AE 的关键差异

| 维度         | Codex + AE                | 本产品目标                            |
| ------------ | ------------------------- | ------------------------------------- |
| 首要任务     | 专业动画创作与合成        | 高质量动态演示的创作、讲解与持续修改  |
| 用户主要操作 | AI / 专业工具操作         | AI 生成初稿，画布直接微调             |
| 内容修改     | 工程或预定义模板控制项    | 文本、图形及动画属性原生可编辑        |
| 动画控制     | 以专业时间线和合成为中心  | 底层完整时间轴，表层保持 PPT 式易用性 |
| 交互         | 交互需要额外设计/运行环境 | 交互是演示作品的一等能力              |
| 交付         | 工程文件、视频等          | 可运行、可分享、可继续编辑的 Web 演示 |

**不把“功能比 AE 更多”作为竞争目标。** AE 的专业动画能力不是第一阶段要复制的对象。

### 2.2 随 AI 变强，哪些价值仍可能保留

- **脆弱的价值**：减少 Prompt、替 AI 组织动画 API、单纯生成 HTML / 关键帧。AI 能力提升会逐渐削弱这些卖点。
- **相对稳定的价值**：对生成结果的确定性直接编辑；交互式演示的运行、发布与分享；持续更新内容而不破坏动画；统一的作品格式和版本管理。
- **边界**：这些也不是天然的技术护城河，现有软件与通用 AI 都可能实现。真正的竞争力取决于具体演示场景下的质量、易用性、稳定性与完整工作流。

## 3. 产品定位与目标用户

### 3.1 产品定位

**AI 原生的 Web 动态演示编辑器。** 它结合：

1. **AI 的创作效率**：从描述直接获得完整、具备动效与基础交互的演示作品。
2. **PPT 的修改便利性**：内容和空间位置可以点击、输入、拖动、对齐、精确微调。
3. **AE 式的运动能力**：底层支持连续时间、对象级轨道、关键帧及运动路径，但不强迫用户掌握复杂动画概念。
4. **Web 的交互与分发**：演讲者可控制播放、暂停、触发交互，作品可直接运行、分享和持续更新。

不是“简化版 AE”，也不是“给普通 PPT 加几个动画效果”。

### 3.2 初期目标人群

优先面向**需要较高视觉质量和现场讲解/交互能力，但不想手工制作复杂动画**的人，例如：

- 产品介绍、功能演示、发布会讲解人员；
- 技术架构/方案演示人员；
- 教育内容制作者、培训讲师；
- 需要动态呈现方案的设计师、运营和售前人员。

暂不以专业特效师或仅需普通静态工作汇报的用户为第一目标群体。

### 3.3 核心产品承诺

> AI 完成主要创作；人只需确定最终效果。不要让用户为了修正一个小问题而学习复杂动画软件，或重新触发一次不确定的生成。

## 4. 典型用户流程

1. **提出需求**：输入主题、核心内容、风格、时长、演讲方式等；可附参考图或资料（属于后续增强，不要求 MVP 全面支持）。
2. **AI 生成**：生成完整的演示，包括内容结构、画面元素、视觉样式、元素动画和必要的交互。
3. **预览**：按整条时间轴播放，也能暂停、跳转到任意时刻或演示阶段。
4. **直接精修**：点击文字修改；选中元素用鼠标拖动、方向键微调或输入精确坐标；直接调整运动起点/终点及时间。
5. **局部 AI 修改（按需）**：对较大变化使用自然语言，只修改目标对象或片段，尽可能保留已确认的细节。
6. **演示与发布**：以 Web 形式演示、交互和分享；后续更新内容后仍保留原有动画与交互逻辑。

### 4.1 必须体验顺畅的微操作

- “这个标题向左移动 5px。”——选中对象后方向键/数值输入即可完成。
- “将标题改成‘2026 年产品介绍’。”——直接双击编辑文本，不用再调用 AI。
- “这张图最后停靠的位置向右一些。”——切换到动画终点并在画布中拖动。
- “这段进入动画慢一点。”——通过片段时长或时间轴边界快速修改。
- “这个对象从上一页移动到下一页。”——跨演示阶段保持运动连续，不因页面边界被迫中断。

## 5. 核心概念与时间模型

### 5.1 总原则

**整份演示共用一条连续的总时间轴，但每个元素有独立的局部动画时间轴。页面只是总时间轴上的一段演示区间，而不是元素的所有权容器。**

需要区分三个概念：

- **全局时间（Global Time）**：当前整份演示播放到哪里，负责统一预览与调度。
- **局部时间（Local Time）**：每个元素内部的动画如何从第 0 帧变化到结束。
- **页面区间（Page Segment）**：用于演示结构、阶段导航、背景或切换的时间区间，不强制截断元素动画。

### 5.2 元素独立于页面

- 元素可以出现在一个页面区间内，也可以跨多个页面区间存在。
- 元素的动画定义不因移动到另一页而改变。
- 页面切换不默认销毁元素，不默认重置元素时间轴。
- 同一个动画定义应具备复用潜力，是否复用实例及覆盖规则后续详细设计。

### 5.3 时间轴之间的关系

需要一个**调度/绑定关系（Binding / Clip）**，定义“元素的局部时间轴从全局时间的哪个位置开始、何时结束、以什么速度播放”。

在简单匀速情况下：

`localTime = (globalTime - binding.start) × speed + localOffset`

这不是要暴露给普通用户的概念，而是保障跨页动画、独立运动和任意帧预览的底层规则。

### 5.4 时间与交互共同驱动

演示不应只能自动播放，还需要支持**演讲者控制**：暂停、继续、跳转、点击触发、局部展开等。

因此渲染状态可抽象为：

`画面 = f(总时间, 元素局部时间, 交互状态, 内容数据)`

为了实现可靠回放、跳帧与导出，交互事件应有可重放或可预设的执行逻辑，不依赖不可追踪的各自独立真实时钟。

## 6. AI 与可编辑对象的边界

### 6.1 受约束的对象规范，而非任意 HTML

AI 不应自由编写互相冲突的 HTML 动画、JavaScript 定时器和样式运动逻辑。需要先建立稳定的**对象/动画协议**，让 AI 在协议允许的范围内创造作品。

首批基础对象建议包含：

- 文本（Text）：可直接编辑内容、字体、排版和样式。
- 图片（Image）：可替换资源、裁剪、移动、缩放。
- 形状（Shape）：矩形、圆形、线条和基础几何图形。
- SVG：允许高表现力的矢量内容。
- 分组（Group）：统一移动、缩放与管理子对象。
- 自定义 HTML 组件：保留为扩展方向，先限制其运动属性和可编辑接口。

每个对象至少包含：唯一标识、类型、内容/资源、布局/静态样式、层级，以及可选的动画轨道引用。

### 6.2 动画由平台提供基础能力

AI 声明“对象做什么动画”，平台负责时间插值、状态计算和渲染。基础属性包括：

- 位置（x、y）和运动路径；
- 大小、缩放与旋转；
- 不透明度；
- 关键帧、缓动曲线；
- 出现/消失的可见区间和动画区间。

**可见区间不等于运动区间。** 一个标题可以在 30 帧内运动完毕，但在之后的 200 帧保持停留。

动画预设（滑入、淡入、放大、路径运动等）可以作为 AI 易用的上层能力，但最终应能映射到可检查、可编辑的底层轨道。

### 6.3 生成结果必须可直接编辑

- AI 生成对象与用户手工创建对象遵循相同的数据模型。
- AI 生成的对象应在画布中可选中、可移动、可修改内容和运动属性。
- 局部 AI 修改应尽量保留对象 ID、已有轨道和用户已完成的微调。
- 如果修改会破坏现有对象/轨道的对应关系，应明确标记冲突或提示确认，不能静默丢失调整。

### 6.4 实例与 Canvas 的关系

产品层面要求的是**每个运动对象都有独立、可注册、可编辑的实例和动画轨道**，不要求“一个对象必须对应一个 HTML Canvas”。

实际渲染可采用 DOM、SVG、Canvas、WebGL 或混合方式，以对象层可编辑性和预览一致性为优先。具体方案由技术验证决定，避免提前将产品绑定到一种渲染技术。

## 7. 编辑器交互要求

### 7.1 默认界面必须偏向 PPT，而非 AE

用户首先看到的是画布、当前演示状态、常用属性和简洁播放控制，而不是复杂的多层关键帧面板。

应优先支持：

- 单击选择元素；双击直接编辑文本；
- 鼠标拖动位置、拖拽调整尺寸；
- 方向键小步移动，支持精确数值输入（如 x - 5px）；
- 对齐、吸附、层级/分组等基础操作；
- 撤销/重做；
- 任意时间位置预览；
- 对运动对象直接选择并编辑起点、终点，必要时展开完整路径与关键帧。

### 7.2 起点、终点和中间关键帧

简单运动默认表现为“从哪里来、到哪里去、用多久”，用户直接拖动起点或终点即可修改。

复杂路径支持补充控制点、调整曲线和关键帧。需要解决的交互冲突包括：

- 拖动当前对象，是移动整个动画、当前关键帧，还是新增关键帧？
- 修改静态布局会如何影响已有局部动画？
- 同一属性由多个轨道控制时以谁为准？

初版应提供明确、可预期的默认行为，并为高级模式保留扩展空间。

### 7.3 播放模式与编辑模式

- **编辑模式**：直接修改当前内容和运动属性。
- **演示模式**：默认不显示编辑控件，支持连续播放、暂停、阶段跳转、点击交互。
- **演示中快速编辑**：允许通过明确的入口切换到轻量编辑状态，快速改字或调整对象后返回演示；避免观众误触导致作品改变。

这里的“演示时能直接修改”不等于所有观众拥有编辑权限；编辑者身份、发布版本和权限需区分。

## 8. 演示与交付要求

### 8.1 作品不是最终视频文件

首要交付物是**可运行的动态 Web 作品**，其对象、轨道、交互逻辑仍然存在，可以更新和重新发布。

需要支持：

- 完整演示播放、暂停、跳转与全屏；
- 页面/章节区间导航；
- 点击等基础交互触发；
- 发布链接或可部署的 Web 演示包；
- 已发布作品更新、版本管理（按阶段实现）。

### 8.2 可选导出

- **优先**：Web 演示包 / 演示链接。
- **后续**：MP4 视频、静态 PDF/图片。
- **不作为 MVP 目标**：将全部高级 HTML/Web 交互动效无损转换为原生 PPTX 动画。

## 9. MVP 范围

### 9.1 必须包含（P0）

1. **从自然语言生成一个完整可播放的动态演示样例**：不只生成静态排版，至少包括多对象动画。
2. **规范化对象模型**：Text、Image、Shape、Group 至少四类可操作对象（SVG 可先作为基础资源支持）。
3. **连续总时间轴 + 页面区间**：至少两个页面区间，支持跨区间元素运动。
4. **元素独立局部动画时间轴**：至少支持位置、透明度、缩放的关键帧控制。
5. **画布直接编辑**：改文本、拖动、尺寸调整、数值微调，修改后不需要重新生成。
6. **动画快速精修**：修改位置起点与终点、开始时间和持续时长；可以在任意帧预览。
7. **保存与加载作品**：对象、动画、区间及配置持久化；回到工程仍可编辑。
8. **Web 演示预览**：统一播放、暂停、跳转和全屏。
9. **撤销/重做与基本数据校验**：精修不能轻易破坏作品。

### 9.2 次优先级（P1）

- 贝塞尔路径、缓动曲线可视化调整；
- 点击对象触发局部动画与返回状态；
- 按对象进行 AI 局部修改并保护已编辑属性；
- 复制/复用动画片段，分组动画；
- 版本管理与发布更新；
- 更丰富的文本、SVG、图表与布局组件。

### 9.3 暂不做（非目标）

- 复刻 AE 的专业特效、插件生态、完整合成能力；
- 把用户培养成专业动画制作人员；
- 手工从零制作复杂动画的全功能工作流；
- 无约束任意 HTML / JS 完全自动逆向解析为可编辑轨道；
- 无损导出带完整 Web 交互的 PPTX；
- 首版覆盖所有屏幕尺寸的完全响应式运动布局；
- 首版实现完整多人实时协作与权限体系。

## 10. MVP 验收场景

以一个 **2 分钟产品/技术方案演示**为测试样例，至少包含：两段以上页面区间、标题与图片动画、一个对象跨页面边界持续运动，以及可暂停和继续播放。

| 验收项     | 预期结果                                                     |
| ---------- | ------------------------------------------------------------ |
| AI 生成    | 生成的作品能直接预览，主要元素具备可解释、可编辑的对象与轨道 |
| 文本微调   | 双击更改标题，已有动画保持有效                               |
| 空间微调   | 选中标题，输入 x 减 5px，画面准确变化，不影响无关对象        |
| 运动微调   | 用户直接移动一个对象的动画终点，新的运动结果可在预览中看到   |
| 时间微调   | 改动动画时长后，播放/跳帧能稳定得到相同状态                  |
| 跨页连续性 | 对象跨越页面区间边界时轨道不自动重置                         |
| 保存加载   | 重新打开后文本、位置、时间、关键帧和区间信息保持一致         |
| 演示交付   | 作品能作为 Web 演示播放，而不是仅导出成视频                  |

建议额外记录三项产品验证指标：**首次可交付作品所需时间、用户完成常见微调的操作步数、AI 修改后原有人工调整的保留率**。这些指标用于实验，不应在缺少测试数据时虚构承诺值。

## 11. 风险与需要验证的假设

### 11.1 最大风险：AI 初稿质量不够高

如果多数作品都需要大量人工重做，产品将被迫发展成复杂手工编辑器，偏离“AI 完成主要创作”的定位。

### 11.2 可编辑性与自由表达的矛盾

AI 越自由，越可能产生编辑器不认识或无法稳定控制的结构。需要优先保证**可编辑性、稳定 ID 与可追踪修改**，然后逐步开放更丰富的表现形式。

### 11.3 直接操作与动画语义冲突

改当前帧的位置、整体位置和终点位置是三种不同操作。默认行为必须直观，否则“只移动 5px”也可能意外改变整段动画。

### 11.4 复杂交互的可回放性

用户点击、悬停、展开等动作使作品不再是单一线性视频。需要验证事件状态、拖动播放头和演示导出之间的一致性。

### 11.5 产品定位被大平台覆盖

PPT、Canva、AE 或通用 AI 编程工具都可能逐渐提供类似能力。单独的“AI 动画代码生成”不是长期壁垒，需要验证用户是否真正愿意为**动态演示场景中从生成、微调到发布的一体化体验**选择独立产品。

## 12. 尚未决定的事项

以下内容暂不写死为需求结论：

- 渲染引擎：DOM/SVG/Canvas/WebGL 或混合方案；
- 页面区间重叠、嵌套、转场及背景切换的精确定义；
- 同一个动画片段复用多个实例时的覆盖规则；
- 事件驱动动画与全局时间的精确映射与录制机制；
- AI 输出采用 JSON 场景声明、受限组件代码或二者结合；
- 图表、3D、粒子效果等高级对象进入产品的先后顺序；
- 离线演示、在线发布、多人权限及计费方式；
- 发布后编辑是否立即覆盖线上版本，还是通过草稿和正式发布区分。

这些应当在 MVP 试验中根据实现成本和真实用户行为逐步确认。

## 13. 最后总结

本产品不是为了让 AI 更容易使用 AE，也不是单纯做一个生成 HTML 页面并播放动画的工具。

**它要解决的是：AI 可以负责绝大部分动态演示创作，但用户仍应像操作 PPT 一样，快速、确定地控制最终作品。**

因此，第一阶段最重要的不是拥有多少种动画特效，而是验证三件事：

1. AI 能否生成视觉和动效质量足够好的完整作品；
2. 生成的每个常用对象能否被人直接精确修改，而不会破坏已有动画；
3. 最终作品能否作为可交互、可持续编辑的 Web 演示稳定运行。

这三件事成立之后，独立对象时间轴、动画预设、复杂交互和多渲染后端才有清晰的产品意义。
